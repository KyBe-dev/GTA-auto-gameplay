# GTA 离线模式智能操作软件：总体架构与 API 规划 v0.1（BYOK 修订版）

更新日期：2026-08-12  
当前验证平台：GTA V Windows 离线故事模式  
未来目标：在 GTA VI Windows 版正式发布且允许测试后，通过适配器扩展支持
发布目标：源代码计划托管在公开 GitHub 仓库；可安装版本仅通过经过审计的 GitHub Releases 或后续明确记录的发布渠道提供

## 1. 项目边界

本项目采用“读取游戏窗口画面 → 建立可验证的游戏状态 → 选择动作 → 模拟普通键盘鼠标输入 → 再次观察结果”的闭环。

当前固定原则：

- 只支持离线单机模式，不支持 GTA Online。
- 不注入游戏进程，不读取或修改游戏内存，不编写内核驱动，不绕过反作弊。
- 云端 AI 只负责低频复杂判断，并且只能使用用户自行配置的凭据（BYOK）；实时控制和基本功能必须可在本地运行。
- 软件、公开仓库、发布产物和项目维护者均不提供共享 API Key 或默认云端代理；终端用户数量增长不得消耗项目维护者的 API 额度。
- 所有动作都通过语义动作层执行，例如 `MoveForward`、`OpenMap`，不在任务代码中写死某个按键。
- 每次动作后都要根据画面确认是否成功，不能假设按键已经生效。
- 软件必须具备紧急停止、窗口焦点检查、失去识别时释放全部按键等安全机制。

### 1.1 术语与指代

- **本仓库**：托管该软件源代码的 Git 仓库；在 Codex 任务中指 Codex 当前打开的 Git 根目录。
- **公开仓库**：本仓库在 GitHub 上的公开源代码、全部 Git 历史、Issue/PR 附件以及 GitHub Actions 产物。
- **发布产物**：提供给他人下载的安装包、压缩包、模型、配置模板及 GitHub Releases 附件。
- **项目维护者**：拥有或维护本仓库和正式发布渠道的人；不等同于下载安装软件的终端用户。
- **贡献者**：向本仓库提交代码、文档、模型或测试数据的人。
- **终端用户**：下载并在自己 Windows 电脑上运行软件的人。下文单独出现“用户”时均指终端用户。
- **用户凭据 / 用户 Key**：由某一终端用户自行申请、拥有并配置的 Provider 凭据，仅消耗该终端用户自己的 Provider 项目额度。
- **维护者凭据 / 维护者 Key**：属于项目维护者的 Provider 凭据；不得进入本仓库、发布产物或终端用户的运行路径。
- **BYOK**：终端用户自行提供用户凭据；不代表项目维护者代为申请、分发、托管或支付。
- **本地基本功能**：无需云端 Provider 即可运行的窗口选择、画面捕获、已实现的本地识别、已支持任务的本地控制、紧急停止和安全降级；不承诺在无云端条件下理解所有未知任务。
- **公开版本**：公开仓库中的代码和由项目维护者正式提供的发布产物，不包括贡献者本机的私有实验文件。

## 2. 推荐总体技术栈

### 2.1 主程序

- Windows 桌面端：C#、.NET 8、WPF。
- 本地数据库：SQLite。
- 日志：结构化 JSON 日志 + 可选的短时画面回放缓冲区。
- 图像处理：OpenCvSharp（OpenCV 的 .NET 封装）。
- 模型推理：ONNX Runtime；Windows 新项目优先评估 WinML。
- 第一阶段如本地 OCR/训练工具在 Python 中更容易验证，可增加独立 Python 工具，但正式运行核心应尽量收敛到 C#。

选择 C# 的原因：Windows 窗口、权限、输入、安装包和后台服务处理更直接；模型可以导出 ONNX 后在本地运行。

### 2.2 Windows 系统接口

| 需求 | 首选方案 | 备用方案 |
| --- | --- | --- |
| 捕获指定游戏窗口 | Windows Graphics Capture | DXGI Desktop Duplication |
| 键盘鼠标输入 | Win32 `SendInput` | 暂不使用驱动级方案 |
| 查找并验证游戏窗口 | Win32 窗口 API | 用户手动选择窗口 |
| 用户自带 API 密钥保存 | Windows Credential Manager 或 DPAPI | 不允许明文配置文件、日志或安装包 |
| GPU 本地推理 | WinML / ONNX Runtime | CPU 推理降级模式 |

## 3. AI、模型与 API 规划

### 3.1 本地实时层（默认必需，不消耗 API）

| 模块 | 用途 | 建议技术 |
| --- | --- | --- |
| Frame Capture | 获取游戏画面 | Windows Graphics Capture |
| UI Detector | 识别暂停、死亡、失败、任务提示、字幕等界面 | OpenCV 模板匹配 + 后续自训练检测器 |
| OCR | 读取任务标题、目标文字、按键设置文字 | 本地 OCR；先比较 Windows OCR 与 PaddleOCR |
| Minimap Parser | 识别玩家朝向、路线、目标标记 | OpenCV + 小型自训练模型 |
| Scene Detector | 识别人、车辆、道路、入口和交互点 | 本地 ONNX 视觉模型 |
| State Estimator | 融合多帧结果，输出可信游戏状态 | 规则、时间窗口与置信度融合 |
| Controllers | 步行、驾驶、镜头、菜单等闭环控制 | 状态机、行为树、PID/启发式控制 |

本地层不能只看单帧。它应保存最近几秒的观察结果，用连续证据避免把闪烁、字幕或过场画面误判成任务状态。

### 3.2 用户自带密钥的云端低频推理层（BYOK，可选）

所有云端 Provider 必须采用 BYOK（Bring Your Own Key）模式：每位终端用户使用自己申请、自己拥有的 Provider 账户、项目和 API Key，其调用只消耗该终端用户自己的额度。项目维护者不向公开版本提供共享 Key，不建立默认的公共 API 中转服务，也不代终端用户承担调用费用。没有配置 Key 时，软件仍可运行术语表定义的本地基本功能。

| Provider | 初始角色 | 调用内容 | 不允许承担的职责 |
| --- | --- | --- | --- |
| Gemini API（用户自行配置） | 默认多模态后备 | 裁剪后的陌生界面、任务文字解释、结构化候选状态 | 每帧视觉、即时驾驶、持续按键控制 |
| Groq API（用户自行配置） | 快速文本后备 | 根据已经提取的结构化状态生成候选计划、日志分析 | 直接控制键鼠、单独决定高风险连续动作 |
| Local Provider | 断网/隐私模式 | 本地小模型分析 OCR 文本或日志 | 超出硬件能力的高频大模型推理 |
| OpenAI Provider | 暂不作为免费默认项 | 未来用户自愿配置后作为可插拔 Provider | 项目初期的必要依赖 |

所有 Provider 都实现统一接口，例如：

```text
AnalyzeUnknownScreen(croppedFrame, currentState) -> ScreenHypotheses[]
InterpretObjective(ocrText, missionContext) -> ObjectiveCandidate
SuggestRecovery(recentEvents) -> RecoveryPlan
```

返回值必须符合 JSON Schema，至少包含：候选结论、置信度、依据、建议下一步和是否需要人工确认。大模型只能提出候选结论，不能直接调用 `SendInput`。

云端凭据必须满足以下约束：

- 由用户在本机设置界面主动填写、测试、替换或删除。
- 仅保存在 Windows Credential Manager 或使用 DPAPI 加密的用户范围存储中。
- 不得进入源代码、Git 历史、默认配置、遥测、日志、崩溃报告、截图或安装包。
- 不得将同一个维护者 Key 分发给多个终端用户；创建多个 Key 也不能替代每位终端用户拥有独立 Provider 项目。
- 公开版本默认不连接项目维护者运营的服务器；若未来新增托管服务，必须作为独立功能重新设计认证、计费、限流和隐私规则，不能复用 BYOK 路径中的用户 Key。

### 3.3 BYOK 与 API 用量控制

- 所有限额都针对当前终端用户自己的 Provider 项目；不同终端用户之间不共享项目维护者的额度。
- 软件不得内置“可直接使用”的公共 Key，也不得在终端用户未配置凭据时回退到维护者 Key。
- 只有本地识别置信度低于阈值并持续若干帧时，才允许调用云端。
- 只发送游戏窗口的必要裁剪区域，不发送整个桌面。
- 对相似画面计算感知哈希，避免反复上传同一画面。
- 设置每分钟、每任务、每天三层调用上限。
- 缓存“画面特征 + OCR + 模型回答”，版本变化后可失效。
- 未配置 Key、Key 无效、Provider 超时、额度耗尽、限流或断网时，自动退回本地模式；若本地模式无法安全判断，则进入暂停/安全恢复，而不是盲目继续。
- 免费额度属于开发便利，不作为最终稳定性保证；Provider 必须可以更换。
- 免费层可能具有不同的数据使用和保留规则，云端上传必须由用户主动开启。

## 4. 统一游戏状态：整个项目最重要的数据结构

建议从第一个里程碑开始就使用统一 `GameState`，即使很多字段暂时为空。

```text
GameState
  gameMode: Gameplay | Paused | Map | Menu | Cutscene | Loading | Failed | Unknown
  controlMode: OnFoot | Driving | Aiming | UI | Unknown
  missionId: optional
  missionStageId: optional
  visibleObjectiveText: optional
  objectiveType: GoTo | Follow | Interact | Drive | Wait | Search | Unknown
  objectiveTarget: optional
  playerLocationEstimate: optional
  targetDirection: optional
  targetDistance: optional
  currentCharacter: optional
  inputProfileId: optional
  confidence: 0..1
  evidence[]
  observedAt
```

状态不能由单一模型覆盖写入。每项证据带时间、来源和置信度，由 `StateEstimator` 统一融合。

## 5. 如何确认“游戏进行到哪一步”

建立独立的 `MissionTracker` 和 `MissionKnowledgeBase`。

### 5.1 MissionKnowledgeBase

每个任务不是一段攻略文字，而是一张可执行的阶段图：

```text
Mission
  id / gameAdapter / version
  entryEvidence
  stages[]
    stageId
    expectedEvidence[]
    objectiveTypes[]
    allowedSkills[]
    completionEvidence[]
    failureEvidence[]
    recoveryOptions[]
  completionEvidence
```

它只保存完成控制所必需的抽象信息和我们自己测试得到的数据，不复制整篇第三方攻略。

### 5.2 MissionTracker 的证据来源

- 任务名称或目标文字的 OCR。
- 屏幕上的任务颜色、目标图标、提示按钮和小地图标记。
- 过场、载入、任务失败、完成界面的识别结果。
- 最近执行过的动作和动作结果。
- 本地数据库保存的上次高置信任务阶段。
- 必要时由云端视觉模型对裁剪画面提出候选解释。

MissionTracker 输出的不是“肯定是第 7 步”，而是候选集合，例如：

```text
stage_07: 0.78
stage_06: 0.17
unknown: 0.05
```

当置信度不足时，系统应先执行信息收集动作，例如等待目标文字再次出现、查看小地图或安全地打开暂停地图，而不是继续任务。

### 5.3 存档和重新启动

- 软件启动时不能只相信上次记录，必须重新观察界面并复核。
- 任务完成、失败、重新载入、切换角色后设置“状态重同步点”。
- 每次阶段迁移都记录触发证据，便于回放和修正。
- 任务知识必须带游戏版本、分辨率、语言和适配器版本，避免更新后继续使用过期规则。

## 6. 如何理解“这一关要做什么”

采用三层策略：

1. **已有任务定义**：直接从 MissionKnowledgeBase 读取当前阶段允许的技能和完成条件。
2. **画面文字解析**：OCR 读取目标文本，转换成统一 `Objective`，例如 `GoTo(targetMarker)`。
3. **未知情况后备**：将必要的裁剪画面、OCR 和当前状态发给多模态 Provider，让它返回结构化候选；低置信度时请求用户确认并保存为新的任务样本。

不让语言模型自由输出按键序列。语言模型只选“目标/技能”，技能控制器负责具体按键并验证结果。

## 7. 可变键位必须通过语义输入层解决

### 7.1 禁止写死按键

任务逻辑只使用：

```text
MoveForward
MoveBackward
TurnLeft
TurnRight
Sprint
Interact
EnterVehicle
OpenPauseMenu
OpenMap
Confirm
Back
```

`InputBindingService` 再把语义动作转换为当前玩家实际键位。

### 7.2 键位获取优先级

1. 如果游戏存在稳定、可合法读取且格式明确的本地配置，读取后仍在 UI 中向用户展示确认。
2. 引导用户打开游戏的键位设置页，软件通过 OCR 扫描每一项。
3. 扫描不完整时让用户在软件内手动填写或按键录入。
4. 默认键位只能作为建议值，不能无确认地假设玩家没有修改。

### 7.3 何时重新检查

- 首次使用。
- 游戏配置文件或 UI 检测到变化。
- 游戏版本、控制器类型或语言变化。
- 连续出现“按键已发送但预期状态未变化”。
- 用户主动点击“重新扫描键位”。

菜单中的 `Confirm`、`Back`、方向导航也属于绑定，必须和游戏内动作分开管理。

## 8. 主动暂停和查看地图

将查看地图实现为独立、可回滚的 `InspectMapSkill`：

1. 判断当前是否允许暂停；过场、载入、失败转换期不执行。
2. 释放所有移动/鼠标按键。
3. 执行语义动作 `OpenPauseMenu` 或 `OpenMap`。
4. 等待并视觉确认已经进入 `Map` 模式。
5. 识别玩家位置、目标标记和路线；必要时执行受限的缩放/平移。
6. 保存地图观察结果及置信度。
7. 执行 `Back`，确认恢复到原来的游戏状态。
8. 恢复前重新检查窗口焦点和任务状态。

查看全地图不应固定周期执行。优先使用小地图；仅在目标未知、路线丢失、疑似卡住或任务阶段切换时打开全地图。

## 9. 现在就要预留的其他长期问题

### 9.1 UI 差异

- 分辨率、宽高比、窗口/全屏、HUD 缩放、亮度、色盲模式、游戏语言都会改变识别结果。
- 所有 UI 区域使用相对坐标，不使用固定像素。
- 首次使用必须运行校准向导并保存 `DisplayProfile`。

### 9.2 多种游戏模式

- Gameplay、Map、Pause、Settings、Cutscene、Loading、Failed 必须是互斥的顶层模式。
- 每个模式只允许有限动作。例如 Loading 状态只允许等待和紧急停止。

### 9.3 卡住、失败和恢复

- 检测画面长期无进展、位置不变、重复动作和任务失败。
- 恢复策略有次数上限，避免无限循环。
- 连续失败后暂停并向用户展示最近证据与回放。

### 9.4 数据采集与模型评估

- 从第一天记录“观察 → 状态 → 动作 → 结果”，否则后期无法定位为什么失败。
- 保存高价值失败片段，普通帧短期循环覆盖，避免磁盘无限增长。
- 建立固定测试录像，让视觉模块在不启动游戏时也能回归测试。
- 每个里程碑都设置量化指标：识别准确率、误操作率、恢复成功率、平均 API 调用量。

### 9.5 版本与适配

- `IGameAdapter` 隔离 GTA V 与未来 GTA VI 的 HUD、任务、物理参数和输入配置。
- 识别模型、模板、任务图和游戏版本绑定。
- GTA VI Windows 版未公布前，不对其 UI、输入或发行日期之外的 PC 行为作保证。

### 9.6 隐私与安全

- 只捕获用户选择的游戏窗口。
- 云端分析默认关闭，开启时明确显示上传范围。
- 云端分析只能使用当前终端用户自行配置的 BYOK 凭据；不得使用项目维护者共享 Key 或默认公共代理。
- 用户应能在设置中查看当前 Provider、测试连接、删除本机凭据并恢复为完全本地模式。
- 避免把玩家账户名、桌面通知或其他应用窗口发送到云端。
- 软件界面常驻显示 AI 是否正在控制；用户输入应能立即接管。

### 9.7 GitHub 公开发布与资源边界

- M0 至 M8 期间可以使用私有 GitHub 远程仓库协作或备份，但仍须遵守凭据和资源排除规则。
- 将本仓库设为公开之前，必须完成最低公开门槛：检查全部 Git 历史和待上传文件中不存在凭据或受限资源；配置 `.gitignore`；添加 README 的项目边界与非官方声明；由项目维护者明确选择并添加 `LICENSE`，或明确说明代码尚未按开源许可证授权。
- 在完成 M9 之前，不向公众提供安装包、预训练模型或其他正式发布产物；公开源代码仓库不等同于正式发布可安装版本。
- 公开仓库不得包含游戏本体文件、可执行文件、用户存档、账户信息或未经授权分发的游戏素材。
- 原始游戏截图、录像和由其制作的测试模板默认只保存在贡献者本机，不直接提交公开仓库；公开测试夹具优先使用自制、合成或已获明确授权的数据，并记录来源和许可证。
- 不复制发布第三方攻略全文；任务知识库只保存软件运行必需的结构化事实和自行测试得到的状态证据。
- `.gitignore` 必须覆盖本机凭据、屏幕录制、截图、崩溃转储、日志、模型缓存、存档和用户配置。
- 引入依赖、模型、数据集或素材前记录名称、版本、来源、许可证及是否允许再分发。
- README 必须说明本项目并非 Rockstar Games 官方项目，也未获得其认可；上传公开 GitHub 仓库前以及每次正式发布前，都要复核适用的游戏条款、商标使用和开源许可证要求。

### 9.8 Windows 安装、快捷方式与 GitHub Releases

- GitHub 仓库中的 `Source code.zip` 只包含源码，不作为普通终端用户的安装方式，也不能自动创建桌面快捷方式。
- 正式安装版由 Windows 安装器生成；初始候选采用 Inno Setup，若后续需要 MSI/MSIX、企业部署或 Microsoft Store 再重新评估 WiX/MSIX。
- 安装器默认创建开始菜单快捷方式，并在安装界面提供“创建桌面快捷方式”的可选复选框；桌面快捷方式应创建在当前终端用户的桌面，而不是所有用户的公共桌面，以避免不必要的管理员权限。
- 快捷方式必须指向安装目录中的主程序 `.exe`，设置正确的工作目录和项目自有 `.ico` 图标；不得指向源码目录、`start.bat`、开发环境或临时构建目录。
- 卸载程序必须删除由安装器创建的桌面及开始菜单快捷方式，不删除终端用户主动保留的数据，除非卸载界面单独说明并得到确认。
- 如果同时提供便携版 `.zip`，README 必须明确说明便携版不会自动安装或创建快捷方式；终端用户可自行创建快捷方式。
- GitHub Releases 应上传版本化安装包，例如 `<ProductName>-Setup-<Version>.exe`，并附发布说明和 SHA-256 校验文件；不能只让终端用户下载仓库源码压缩包。
- 正式公开发布前应完成安装包代码签名策略；未签名测试版必须明确标注，不能指导终端用户绕过 Windows 安全警告。
- Inno Setup 脚本建议保存在 `installer/`，安装包输出目录不得提交到 Git 历史，而应作为经过检查的 GitHub Release 附件发布。
- 使用 Inno Setup 前记录其许可证；如果项目未来商业化，应重新核对并满足其当时的商业许可要求。

## 11. 里程碑路线

### M0：仓库与安全骨架

- 建立解决方案、模块边界、日志、配置、紧急停止。
- 建立 `GameState`、`IGameAdapter`、`IInputController`、`IAIProvider`、`IUserCredentialStore` 接口。
- 加入自动检查，防止真实 API Key、共享维护者凭据或明文密钥配置进入仓库。
- 建立覆盖凭据、截图、录像、日志、崩溃转储、存档和用户配置的 `.gitignore`，并定义测试数据的来源与许可证记录格式。
- 建立“转为公开仓库前”检查清单；由项目维护者决定代码许可证后添加 `LICENSE`，在此之前保持远程仓库私有。

### M1：最小闭环

- 选择并识别 GTA V 窗口。
- 捕获游戏窗口。
- 区分 Gameplay / Pause / Map / Unknown。
- 在测试场景执行前进、转向、停止并验证结果。
- 失焦或低置信度时释放所有输入。

### M2：显示与键位校准

- 分辨率、语言、HUD 校准。
- 键位扫描/手动录入与动作映射。
- 设置页和地图页的可靠进入、识别、退出。

### M3：任务观察器

- OCR 目标文字。
- 任务开始、阶段变化、失败、完成识别。
- SQLite 保存候选任务进度和证据。

### M4：导航基础

- 小地图解析。
- `InspectMapSkill`。
- 简单步行路线和卡住检测。

### M5：单个任务端到端

- 选择一个动作类型较少、可重复测试的 GTA V 离线任务。
- 建立完整任务阶段图。
- 支持失败恢复和重新同步。

### M6：技能扩展

- 驾驶、跟随、互动等独立技能逐个加入。
- 每个技能先用录制画面和封闭测试场景验证。

### M7：BYOK 云端后备和用户侧额度控制

- 实现终端用户自行配置 Gemini / Groq Key 的设置流程；公开版本不提供共享维护者 Key 或默认公共代理。
- 使用 Windows Credential Manager 或 DPAPI 保存用户凭据，并支持测试、替换和删除。
- 实现 JSON Schema、用户侧缓存、用户侧限流、隐私开关及未配置 Key、额度耗尽和断网时的本地降级。
- 比较云端帮助带来的成功率提升是否值得调用成本。

### M8：多任务覆盖与 GTA VI 适配准备

- 扩充任务图、失败案例库和回归录像。
- 固化适配器测试套件。
- GTA VI Windows 版正式可测试后，新建适配器和数据集，不直接复用未经验证的 GTA V 参数。

### M9：公开发布准备

- 审计仓库历史和发布产物，确认没有 API Key、用户凭据、存档、日志或未经授权的游戏资源。
- 复核已选代码许可证，并完成依赖、模型和测试数据的许可证清单。
- 完成 README 中的 BYOK 设置、完全本地模式、隐私边界、系统要求、离线模式限制及非官方项目声明。
- 生成并测试 Windows 安装包：验证安装路径、开始菜单快捷方式、可选桌面快捷方式、图标、启动、覆盖升级和完整卸载。
- 在干净的标准用户 Windows 账户中测试从 GitHub Releases 下载、安装、启动和卸载，不依赖 Visual Studio、VS Code、源码目录或开发机环境。
- 验证安装包卸载、凭据删除、日志清理、紧急停止、自动更新和代码签名策略后，再进行公开推广。

## 12. 当前需要暂缓的决定

- 安装器初始候选为 Inno Setup；具体产品名、安装范围、自动更新和代码签名方案在原型稳定后决定，若未来商业化还需重新核对安装器许可。
